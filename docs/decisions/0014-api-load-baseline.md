# Decision 0014: bounded open-arrival API load baseline

Status: predeclared before real-catalog load measurements.

Measure the unchanged Java API/JAR on `csl-pilot-catalog-v1-a`, the immutable full 1,814,924-record ES catalog. Retain ES9.5.6/Basic/Kuromoji, two container CPUs, 3GiB container/1GiB heap and API256MiB heap with its existing16-worker/64-connection/backlog32 limits and 2s backend deadline. No production deployment or added spending. Keep frozen runtime/experiment sources and official-test labels unchanged; shared CI evolves separately.

Pin native **Grafana k6 2.0.0**, verify official release archive SHA-256 per platform, install only under ignored local data. Disable usage reporting and use only built-in modules/local files. Use `constant-arrival-rate` with one HTTP request per iteration, 64 preallocated/max VUs and no sleep inside iterations. This schedules arrivals independently of response speed until the generator exhausts its VUs; report every dropped iteration. HTTP timeout3s and grace5s bound completion. Preserve raw NDJSON samples and opaque k6 summaries, then independently recompute counts/percentiles.

Select **100 validation queries per locale** by SHA256(seed TAB locale TAB queryID), seed `commerce-api-load-v1`, then globally order the 300 selected queries by SHA256(seed TAB locale TAB queryID). Reuse saved native ES top10 IDs/scores as the exact successful-response contract. Use explicit `limit=10`. This deliberately balanced synthetic stress mix uses real query text; it represents neither validation-frequency weighting nor real user traffic. Every fully scheduled point contains complete 300-query cycles. Record actual locale/unique-query coverage when drops occur. No labels are read or tuned.

Start a fresh API process, ensure green index readiness/UUID/count invariants and warm at **100 arrivals/s for30s** on the identical query mix. Keep connection reuse enabled. Run measured offered rates **20,100,200,500,1000/s**, each **30s**, with5s idle cooldown between points. Warm-up and cooldown are excluded from measured samples. Repeat with a fresh API process, the same warm-up and reversed rate order. Do not flush OS/index caches or restart ES between campaigns; label this warm-cache and disclose prior-load/cache/thermal history. Preserve full workload/input/source/JAR/index hashes and all failed points. No extra rates or tuning in this experiment.

Report scheduled slots(rate×duration, allowing ±1 endpoint scheduling boundary), started/completed requests, dropped iterations, HTTP status/error-code counts, transport timeouts and correct successful throughput. Reconcile one raw HTTP request/completion/client-elapsed sample per started iteration. Report p50/p95/p99/max for **all attempts** and separately correct HTTP200s; include failures rather than publishing successful-request percentiles alone. Custom wall-clock client timing wraps the HTTP call and includes connection/client blocking; k6 `http_req_duration` excludes connection/blocking, and `http_req_waiting` includes server queueing plus service/TTFB. Preserve both and their scope. Percentiles describe each short run, with no confidence/reproducible-latency claim.

Before measurements, qualify a tested point only if **no HTTP200 result is incorrect** and **correct HTTP200 completions / scheduled slots ≥99%**. Count dropped work and every non200/transport failure as loss. Report the highest qualifying **tested offered rate in both runs**, not an exact saturation limit. Publish latency curves without a numeric latency SLO: this campaign supplies the measurements needed to choose future targets. If no point fails, report saturation not reached; if behavior is non-monotonic, disclose it. This availability rule is an experiment budget, not an external production promise.

Sample every second: ES process CPU, JVM heap, cgroup current/peak, search queue/rejection counters and raw `ps` CPU/RSS observations for task-owned API/k6 PIDs. Generator/server share the host: record hardware/VM envelope and disclose interference. `ps` CPU is a process lifetime average. Observe k6 VU/blocked/connect/wait timing and drops. Tomcat queue occupancy is **not directly instrumented** here; do not present TTFB minus another metric as isolated queue time. A later instrumentation increment can explain bottlenecks.

Stop further points on incorrect successful output, process death or monitor failure; retain partial reports. Ordinary overload errors/drops are measured outcomes, not a reason to hide/retune a point. After each campaign require readiness and correct responses for all300 queries at low sequential load, retaining recovery results. Stop only task-owned Java/ES processes at the end, preserve volume and leave unrelated services alone.

Test deterministic sampling and raw-metric reconciliation/percentiles/qualification with dropped work and failures. A tiny native-k6 controlled HTTP fixture validates success and wrong-result detection without Elasticsearch; CI exercises the same JS/parser on synthetic data using a checksummed Linux binary. Benchmark rates and real query artifacts are never run/downloaded in CI. Complete with actual curves/tables, limitations, report, runbook and check-passing PR. No Java performance fixes, circuit breakers, telemetry stack, neural serving or update ingestion in this step.
